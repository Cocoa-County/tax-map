Create a map / AI-agent playbook

For project creators / AI-agent reference

Interpret the records.
Make the work auditable.

You do the reasoning. taxmap's MCP tools perform deterministic storage, extraction, GIS operations, computation, validation, and site builds.

For direct ingestion, read the plain-text playbook and the documentation index. Use the connected server's live tool schemas for exact parameters, and repository skills for detailed procedures.

First-time tools setup: follow the downloaded repository's SETUP.md. Install runtime requirements, build the local plugin with absolute MCP executable paths, and persistently install the chosen CLI's bundle through its plugin manager. All skills and projectless MCP belong to the plugin; do not also register loose copies or independent MCP. Preserve configuration, migrate legacy entries only with approval, save the handoff, and activate through the client. Current Copilot can refresh in-session; Claude can use /reload-plugins; current Codex requires a new session after installation. Verify skills and callable MCP tools in the actual assistant session; a standalone subprocess check is insufficient. Do not create a city project for a tools-only request. The short setup request is the public entry point.

Once live readiness is verified: for “Build a taxmap app for Martinez, CA”, load build-taxmap-app and its installed TAXMAP-TOOLS.md, verify live lifecycle tools, then call app_start with city and state separately. If the original request already asked for an app, continue in-session when supported without requiring another build request. Derive optional settings and continue automatically through official-source research, one exact content review and a local preview. Preserve explicit paths, years and scope; otherwise verify the latest adopted year. Ask only about genuine ambiguity, permissions or essential blockers. If the installed tools lack this flow, report the version/connection blocker and obtain approval for an update; source changes do not refresh a loaded plugin.

Manual work is still supported: an explicit “Create a new taxmap project. Walk me through the setup.” uses taxmap-project-setup. Individual skills, CLI/MCP tools and editable project files remain available. Verify the returned root before writes. Read PROJECT-PROMPT.md when present and use current config/app.yaml on guided resumes without rewriting the original request. Older projects may lack these files; do not reinitialize them. The server never runs AI research itself. No commits, pushes, uploads or deployment without separate approval.

If the user ran the one-command project installer, inspect taxmap-install.json and taxmap.yaml, confirm the intended project root, and reuse its .venv and .taxmap-tools source/skills. Do not initialize it again or download a duplicate checkout. Agent sign-in and a verified MCP connection remain separate steps.

Shared jurisdiction resources: use find-jurisdiction-resources before discovery to read a consistent revision of taxmap-resources. Reverify matching city/parent-county portals, GIS services and bill templates; catalog metadata is not adoption evidence. Continue official research if unavailable. Before preview, propose verified site.parcel_links with APN/year caveats or document why none are included. Keep specific records in the project. Requested public corrections use contribute-jurisdiction-resources, publishing approval and the host's authorized GitHub tools for a fork-based PR; maintainers approve and merge. Never self-approve, auto-merge or push contributions directly to catalog main. No extra MCP registration or credentials stored in taxmap.

Operating contract

Publication is explicit: site.publish_fields is strict, with hide_fields taking precedence. Approve the parcel APN required for public joins. Resources default to private, even when cited; obtain approval for IDs in site.publish_resources before exporting their metadata, citations or copies. Only inventory rows linked to approved resources are exported. Approve extra roll columns using site.publish_roll_fields; amounts and APN joins are always public. Review model prose and notes separately. Rebuild and redeploy after revoking approval.

For guided apps, app_review prepares an unserved private export. Inspect its public model files and present one consolidated review of exact fields, per-roll columns, resource IDs/titles/origins, document-copy policy, notes and material model prose. Record the digest only after the user's approval. Changed content needs review again; unchanged content can resume. Approval permits a local preview, not deployment. Host tool-permission prompts are independent. Guided apps require an explicit field list; low-level builds retain legacy null = all fields behavior.

For disable, re-enable, or removal, use taxmap-uninstall and UNINSTALL.md. Use native plugin management, verify ownership/scope, get approval, and preserve city projects. The external document is the fallback when the plugin is disabled. Separate legacy MCP registrations and skill copies do not follow the plugin toggle.

  • Resolve jurisdiction, fiscal year, scope and project path from the request, safe defaults and evidence; do not turn optional settings into a questionnaire. Never reuse Concord's model as another city's verified data.
  • Use app_start for guided creation/resume or project_open/project_init for manual work, then verify the returned root. Only the repository's VS Code example is Concord-pinned; the installed plugin starts projectless.
  • Record adoption evidence, scope and gaps through app_status; source inventory and model files preserve decisions beyond the conversation.
  • Adopted rolls and county bills are authoritative. Formulas explain or estimate; do not tune them to force agreement.
  • Keep supported partial scope visibly partial. Never invent rates, bill codes, membership, missing inputs or source findings. A missing charge is not zero.
  • Use the same evidence/privacy rules for manual and guided work. Never infer permission to publish from a successful build.

GIS and model work can proceed independently once the required sources are verified. Extraction and validation are evidence tools, not substitutes for reading the source method.

Evidence and model requirements

{
  "resource": "adopted-report",
  "page": 15,
  "locator": "Part E, printed p. 11",
  "quote": "Short supporting excerpt",
  "note": "Explain any relevant limitation"
}

The page is a 1-based PDF page, not the printed number. Cite rates, constants, lookup schedules, totals, rolls, membership, and verified bill code/description pairs. Use evidence_for to inspect provenance, and index_rebuild after external file edits when needed.

Districts support zones, membership, formula IDs, notes, and bill_labels. Formulas support declared inputs/sources, constants, lookups, terms, expressions, applicability, tolerance, caveats, and evidence. Use the live schemas and typed model reference; do not invent expression functions.

Match both county bill code and description. A verified district-level label is not proof that a selected parcel has that charge. Do not infer a benefit zone from an ambiguous label: Concord's JV / KIRKWOOD LMD also appears on Ygnacio Woods bills.

Failure handling

  • No text layer: read visually or use suitable OCR. Record gaps and continue other supported scope; do not present a truncated roll as complete or turn extraction failure into absence.
  • Count/total mismatch: inspect transcription, duplicates, rounding and scope. If source values still conflict, preserve them and disclose the failed reconciliation in a partial preview. Verifying adoption does not make arithmetic discrepancies disappear.
  • Unmatched APNs: inspect normalization, coverage, retired parcels and documented check digits. Report matched/unmatched counts; never strip an arbitrary final digit globally.
  • Formula mismatch: report match counts, missing/proxy inputs and method limitations. A supported annual-rate schedule is not necessarily an independently reconstructed engineering formula.
  • Network/portal error: report availability failures and respect rate limits and TLS checks. Do not bypass access restrictions or treat rejection as no charge.
  • Build warning: inspect hidden inputs and missing outlines. Integrity success is not financial reconciliation. No supported usable model means an honest blocker, not an empty success-shaped app.

Completion checks

  1. Project root and scope established; sources inventoried with adoption evidence and citations.
  2. Roll totals/counts checked and joins measured. Preserve source discrepancies; guided previews block blank/duplicate identities and unparsed amounts.
  3. Formula/roll comparisons reported accurately; missing inputs, approximations and partial coverage labeled.
  4. No unresolved integrity errors; aggregate readiness and build warnings reviewed. A green project_validate alone is insufficient.
  5. Exact export content approved before a local preview; returned loopback URL responds over HTTP. Where browser tools are available, check representative APNs, calculator changes/reset, links and mobile layout; explicitly identify checks not performed.
  6. If deployment was separately approved, verify actual public URLs. Otherwise deliver the preview, not a claim of deployment.

Guided app.yaml stores intent, progress, approval, last readiness and restart handoff. Recompute status from current files; a recorded URL is not proof a server is running. Guided outputs are under .taxmap/app-previews; manual builds default to site/. Stop with app_preview(stop=true) for the owning guided project or site_serve(stop=true) for a low-level preview. MCP shutdown ends its preview too. Never equate partial coverage with absence of an assessment.

For separately approved deployment, preserve the exact guided export's coverage page and disclaimer. Do not publish the whole cache or substitute an unchecked low-level CI rebuild: it does not enforce app.yaml approval or add the guided coverage page. See the deployment guide.
