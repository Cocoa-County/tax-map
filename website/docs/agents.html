Create a map / AI-agent playbook

For project creators / AI-agent reference

Interpret the records.
Make the work auditable.

You do the reasoning. taxmap's MCP tools perform deterministic storage, extraction, GIS operations, computation, validation, and site builds.

For direct ingestion, read the plain-text playbook and the documentation index. Use the connected server's live tool schemas for exact parameters, and repository skills for detailed procedures.

First-time tools setup: follow the downloaded repository's SETUP.md. Install runtime requirements, build the local plugin with absolute MCP executable paths, and persistently install the chosen CLI's bundle through its plugin manager. All skills and projectless MCP belong to the plugin; do not also register loose copies or independent MCP. Preserve configuration, migrate legacy entries only with approval, save the handoff, and stop for the user to restart. Do not create a city project in this session. The short setup request is the public entry point.

After restart: load taxmap-project-setup and its installed TAXMAP-TOOLS.md supporting file, verify live tools, ask for project settings and location, and create/open the intended project. Check its root with project_info. New projects include a generated PROJECT-PROMPT.md for research, optional focus, and unverified starting-resource references; read it when asked to continue. Older projects may lack it; do not reinitialize them. Detect research capabilities and report blockers. No commits, pushes, uploads, or deployment without approval.

If the user ran the one-command project installer, inspect taxmap-install.json and taxmap.yaml, confirm the intended project root, and reuse its .venv and .taxmap-tools source/skills. Do not initialize it again or download a duplicate checkout. Agent sign-in and a verified MCP connection remain separate steps.

Operating contract

For disable, re-enable, or removal, use taxmap-uninstall and UNINSTALL.md. Use native plugin management, verify ownership/scope, get approval, and preserve city projects. The external document is the fallback when the plugin is disabled. Separate legacy MCP registrations and skill copies do not follow the plugin toggle.

  • Confirm jurisdiction, fiscal year, scope, project path, and publication intent. Never reuse Concord's model as if it were verified for another city.
  • Call project_open or project_init, then project_info. Verify the returned root before writing. The repository's default MCP configuration points to Concord.
  • Record research and decisions through tools so the project contains the evidence, not merely the conversation.
  • Adopted rolls and county bills are authoritative. Formulas explain or estimate; do not tune them to force agreement.
  • Do not invent rates, bill codes, parcel membership, missing inputs, or source findings. Distinguish a lead from a verified fact.
  • Request approval for publication, personal data, and redistribution. Do not silently deploy because the build succeeded.

GIS and model work can proceed independently once the required sources are verified. Extraction and validation are evidence tools, not substitutes for reading the source method.

Evidence and model requirements

{
  "resource": "adopted-report",
  "page": 15,
  "locator": "Part E, printed p. 11",
  "quote": "Short supporting excerpt",
  "note": "Explain any relevant limitation"
}

The page is a 1-based PDF page, not the printed number. Cite rates, constants, lookup schedules, totals, rolls, membership, and verified bill code/description pairs. Use evidence_for to inspect provenance, and index_rebuild after external file edits when needed.

Districts support zones, membership, formula IDs, notes, and bill_labels. Formulas support declared inputs/sources, constants, lookups, terms, expressions, applicability, tolerance, caveats, and evidence. Use the live schemas and typed model reference; do not invent expression functions.

Match both county bill code and description. A verified district-level label is not proof that a selected parcel has that charge. Do not infer a benefit zone from an ambiguous label: Concord's JV / KIRKWOOD LMD also appears on Ygnacio Woods bills.

Failure handling

  • No text layer: render the page and read visually or use appropriate OCR. Record unreadable sources; do not turn extraction failure into an absence claim.
  • Count/total mismatch: inspect transcription, duplicated rows, rounding, and document scope. Report unresolved differences.
  • Unmatched APNs: inspect normalization, layer coverage, and retired parcels. Report matched and unmatched counts.
  • Formula mismatch: report the number and magnitude of differences, missing/proxy inputs, and method limitations. Preserve the official amount.
  • Network/portal error: report availability failure, respect rate limits, and do not guess URLs or interpret rejection as no charge.
  • Build warning: inspect the actual warning, especially hidden input fields and missing outlines. Do not claim a complete map solely because the build returned output.

Completion checks

  1. Project root and scope confirmed; sources inventoried with status and citations.
  2. Roll counts/totals checked; joins measured; duplicates and unparsed amounts resolved or disclosed.
  3. Formula comparisons reported accurately; missing data and approximations labeled.
  4. project_validate has no unresolved errors; build warnings reviewed.
  5. Browser preview verified with representative APNs, calculator changes/reset, source links, overlap selection where applicable, and mobile layout.
  6. Public field allow-list, disclaimers, and redistribution choices reviewed and approved.
  7. If deployment was requested, actual public URLs verified. Otherwise deliver the preview and publication instructions, not a claim of deployment.

Handoff should list the project path, sources, modeled coverage, validation results, limitations, preview/public URL, and maintenance steps. Never equate partial coverage with absence of an assessment.
